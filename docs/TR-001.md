## Abstract

This report documents the first two development phases of a TinyML-oriented embedded systems project based on an ESP32 DOIT DevKit V1 and a commercially labeled MPU-6050 IMU module.

Phase 1 established low-level I2C communication, confirmed device identity through direct register interrogation, and validated raw accelerometer data acquisition without vendor libraries. Unexpectedly, the sensor returned WHO_AM_I = `0x72` instead of the MPU-6050 standard value of `0x68`, indicating a pin-compatible replacement device.

Phase 2 extended the firmware to include full 6-axis acquisition (accelerometer and gyroscope), offset calibration, scale conversion to physical units (m/s² and °/s), and a modular code architecture separating hardware logic from the main application loop. An OLED display integration attempt was conducted and documented as a hardware failure due to a defective unit.

TinyML applications depend on reliable, calibrated sensor pipelines. ## 4. Phase 1 — Initial Hardware Characterization

### 4.1 I2C Bus Validation

| File | Role |

### 5.2 Gyroscope Data Acquisition

Gyroscope output registers `0x43`–`0x48` were read and confirmed functional.

### 5.3 Scale Conversion

| Sensor | Range | Scale factor |
|---|---|---|
| Accelerometer | ±2g | 16384 LSB/g |
| Gyroscope | ±250°/s | 131 LSB/°/s |

Gyroscope output converted to °/s: `(raw - offset) / 131`

## 6. OLED Display Integration Attempt

A DST-015 OLED display module was connected to the I2C bus (GPIO21/GPIO22) with the intent of displaying real-time sensor data.

**Findings:**

- The unit did not appear in I2C address scans (neither `0x3C` nor `0x3D` detected).
- When connected, the unit caused complete I2C bus collapse (Error -1 on all transactions), preventing IMU communication.
- The failure persisted with pull-up resistors (10 kΩ) on SDA and SCL.
- The failure persisted with VIN (5V) instead of 3V3 as supply.
- Connecting only VCC and GND (no SDA/SCL) still caused bus collapse, indicating an internal short circuit in the display module.

**Conclusion:** The OLED unit is defective. OLED integration is deferred pending replacement hardware.

## 11. Phase 3 — Complementary Filter and Orientation Estimation

### 11.1 Motivation

Raw gyroscope data accumulates drift over time when integrated to estimate angle. Raw accelerometer data is accurate in static conditions but highly sensitive to vibration and dynamic acceleration. A complementary filter addresses both limitations by fusing the two sources.

### 11.2 Algorithm

```
orientation = alpha * gyroscope_integration + (1 - alpha) * accelerometer_angle
```

With alpha = 0.98:
- Gyroscope contribution (98%): smooth, low-latency response to motion.
- Accelerometer contribution (2%): long-term drift correction.

Roll and pitch are computed independently. Yaw estimation requires a magnetometer and is excluded.

**Roll from accelerometer:**
```
roll = atan2(ay, az) * 180 / pi
```

**Pitch from accelerometer:**
```
pitch = atan2(-ax, sqrt(ay² + az²)) * 180 / pi
```

**Gyroscope integration:**
```
gyro_roll  = prev_roll  + gx * dt
gyro_pitch = prev_pitch + gy * dt
```

### 11.3 Implementation

| File | Role |
|---|---|
| `include/filter.h` | Orientation struct, filter_init() and filter_update() interface |
| `src/filter.cpp` | Complementary filter implementation |

`dt` is computed from `millis()` at each loop iteration for accurate time integration.

### 11.4 Verified Output (stationary)

| Parameter | Value |
|---|---|
| Roll at rest | ≈ 0.00° |
| Pitch at rest | ≈ 0.00° |
| Noise range | ±0.35° |

Orientation responds correctly to physical rotation of the sensor. No observable drift during short-duration tests.

## 13. Phase 4 — Dataset Collector Firmware

### 13.1 Motivation

Before training data can be assembled, the firmware must emit windowed, feature-extracted samples in the exact numerical format the model will later consume — rather than raw per-sample streams. Performing feature extraction on-device (instead of post-hoc in Python) validates that the same extraction routine used for training is reusable at inference time, eliminating train/inference skew.

An initial design considered a physical push-button to mark individual gesture events. This was rejected: button-triggered capture is noisy (imprecise timing relative to the physical gesture) and impractical for repeated single-hand data collection sessions. A **session-based serial command protocol** was adopted instead — one command starts a labeled recording session that persists across many consecutive gesture repetitions.

### 13.2 Architecture

| File | Role |
|---|---|
| `include/collector.h` | Window size / sample rate constants, public interface |
| `src/collector.cpp` | Session state machine, feature extraction, CSV serialization |

`main.cpp` was extended to call `collector_init()` once at startup and `collector_check_command()` / `collector_add_sample()` each loop iteration, after the IMU read and filter update. The complementary filter's orientation output (roll/pitch) is computed but **intentionally not passed to the collector** — consistent with the locked design constraint that gesture classification must be orientation-invariant.

### 13.3 Session-Based Recording Protocol

| Command | Effect |
|---|---|
| `s` | Start/continue a SHAKE-labeled session (label 0) |
| `r` | Start/continue a ROTATE-labeled session (label 1) |
| `i` | Start/continue an IDLE-labeled session (label 2) |
| `x` | Stop the current session |
| `h` | Reprint the CSV header (for reference during a live session) |

A session remains active — silently emitting one CSV row per completed window — until `x` or a new label command is received.

### 13.4 Windowing and Feature Extraction

| Parameter | Value |
|---|---|
| Sample rate | 50 Hz (20 ms loop delay) |
| Window size | 50 samples = 1 s |
| Features per window | 12 (mean + RMS of ax, ay, az, gx, gy, gz) |

Feature extraction runs entirely on-device per completed window, using the same calibrated accelerometer/gyroscope values produced by the Phase 2 pipeline. No absolute roll/pitch is included in the feature set.

### 13.5 Output Format

CSV emitted over serial, one row per completed window:

```
gesture,ax,ay,az,gx,gy,gz,ax_rms,ay_rms,az_rms,gx_rms,gy_rms,gz_rms
```

`gesture` is the numeric label captured at the start of the row's window (0 = shake, 1 = rotate, 2 = idle). Rows are assembled offline into per-class CSV files for the training pipeline.

### 13.6 Issue Identified and Corrected Prior to Commit

Code review prior to staging identified that `_sampleCount` was not reset on a label transition (`s`/`r`/`i`) or on `x`. In practice this allows a partially filled window from one session to carry over into the next, so a window can be assembled from samples belonging to two different gestures while being emitted under a single label — a silent mislabeling defect that would have degraded dataset quality from the first recording session onward. Fixed by resetting `_sampleCount = 0` on every label transition and on stop, discarding any partial window at session boundaries.

A related build-configuration issue was corrected in `platformio.ini`: the `i2c-scan` and `ssd1306-test` tool environments declared their `src_dir` override in bare `[i2c-scan]` / `[ssd1306-test]` sections rather than inside their corresponding `[env:...]` blocks, where PlatformIO requires it to take effect. Left uncorrected, both tool environments would have built against the default `src/` directory instead of `tools/`. `Adafruit SSD1306` / `Adafruit GFX` were also removed from the main `esp32doit-devkit-v1` environment's `lib_deps`, consistent with the locked decision that the OLED has no dependency in the ML pipeline; they remain only in `ssd1306-test`, where the blocked bring-up test actually needs them.

### 13.7 Current Status

Collector firmware compiles and runs correctly against the fixed session-boundary logic described above. No training data has been recorded yet — the next session begins the actual capture (≥200 windows per class for shake, rotate, idle).

## 14. Build System Restructuring — Multi-Environment Source Isolation

### 14.1 Motivation

As the project grew to include standalone diagnostic firmware (`i2c_scan`) alongside the main gesture-recognition application, and with OLED bring-up testing (`ssd1306_test`) planned as a distinct firmware, a mechanism was needed to build multiple independent `setup()`/`loop()` programs from a single repository without cross-contamination between builds.

### 14.2 Root Cause of the Original Approach's Failure

The initial approach attempted to override `src_dir` on a per-environment basis inside `[env:NAME]` blocks in `platformio.ini`. This does **not** work in the PlatformIO Core version used by this project: `src_dir` is only configurable globally, at the `[platformio]` section level, not per environment. Confirmed directly via build output:

```
Warning! Ignore unknown configuration option `src_dir` in section [env:i2c-scan]
```

With this misconfiguration, environments intended to build diagnostic tools were silently compiling the main firmware's `src_dir` instead — a defect that could have gone unnoticed for some time, since the build itself did not fail, it simply compiled the wrong program.

### 14.3 Adopted Solution: `build_src_filter`

Unlike `src_dir`, `build_src_filter` **is** supported per environment and allows include/exclude glob patterns within a single shared `src_dir`. The repository was restructured so that each independent firmware lives in its own subdirectory of `src/`, and each environment's `build_src_filter` includes only its own subdirectory while explicitly excluding the others:

| Directory | Firmware | Environment |
|---|---|---|
| `src/gesture-recognition/` | Main application — IMU driver, complementary filter, dataset collector | `gesture-recognition` (default) |
| `src/i2c_scan/` | Standalone I2C bus diagnostic tool | `i2c-scan` |
| `src/ssd1306_test/` | OLED bring-up test (hardware currently defective, deferred) | `ssd1306-test` |

```ini
[env:gesture-recognition]
build_src_filter = +<gesture-recognition/> -<i2c_scan/> -<ssd1306_test/>

[env:i2c-scan]
build_src_filter = +<i2c_scan/> -<gesture-recognition/> -<ssd1306_test/>

[env:ssd1306-test]
build_src_filter = +<ssd1306_test/> -<gesture-recognition/> -<i2c_scan/>
```

`default_envs = gesture-recognition` in `[platformio]` ensures an unqualified `pio run` builds only the primary firmware. The previous `tools/` directory (which held the diagnostic tool source outside of `src_dir`, and therefore could not be reached by `build_src_filter`) was removed; its contents were relocated into `src/`.

### 14.4 OLED Retest — Deferred, Environment Ready

The `ssd1306-test` environment and its Adafruit SSD1306/GFX library dependencies are now correctly isolated and ready to build in advance of the actual hardware retest. The underlying hardware issue (I2C bus collapse / brownout, documented in Section 6) remains unresolved and is **not** being re-investigated at this time — this restructuring only prepares the build environment so the retest can proceed later without further tooling work. It is possible, though not confirmed, that some portion of the earlier OLED bring-up attempts were themselves affected by the `src_dir` misconfiguration described in 14.2; this will be considered when hardware retesting resumes.

### 14.5 Verification

Each environment was confirmed to compile only its intended source file(s) via verbose build output (`pio run -e <env> -v`, checking the `Compiling` entries against the expected file set).
