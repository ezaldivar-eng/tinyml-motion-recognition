#  **Abstract**

This report documents the first two development phases of a TinyML-oriented embedded systems project based on an ESP32 DOIT DevKit V1 and a commercially labeled MPU-6050 IMU module.

Phase 1 established low-level I2C communication, confirmed device identity through direct register interrogation, and validated raw accelerometer data acquisition without vendor libraries. Unexpectedly, the sensor returned WHO_AM_I = 0x72 instead of the MPU-6050 standard value of 0x68, indicating a pin-compatible replacement device.

Phase 2 extended the firmware to include full 6-axis acquisition (accelerometer and gyroscope), offset calibration, scale conversion to physical units (m/s2 and deg/s), and a modular code architecture separating hardware logic from the main application loop. An OLED display integration attempt was conducted and documented as a hardware failure due to a defective unit.

# **1. Introduction**

TinyML applications depend on reliable, calibrated sensor pipelines. Before collecting training datasets or developing inference models, the sensing subsystem must be fully validated at every layer: physical connections, communication protocol, register behavior, scale factors, and noise characteristics.

This report covers:

- I2C bus validation and device identification

- Accelerometer and gyroscope register characterization

- Offset calibration and scale conversion

- Firmware modularization

# **6. OLED Display Integration Attempt**

A DST-015 OLED display module was connected to the I2C bus (GPIO21/GPIO22) to display real-time sensor data.

Findings:

- Unit did not appear in I2C address scans (0x3C and 0x3D absent).

- When connected, caused complete I2C bus collapse (Error -1 on all transactions).

- Failure persisted with 10 kOhm pull-up resistors on SDA and SCL.

- Failure persisted with VIN (5V) supply instead of 3V3.

- Connecting only VCC and GND (no SDA/SCL) still caused bus collapse — internal short circuit confirmed.

Conclusion: The OLED unit is defective. Integration deferred pending replacement hardware.

# **11. Phase 3 — Complementary Filter and Orientation Estimation**

## 11.1 Motivation

Raw gyroscope data accumulates drift over time when integrated to estimate angle. Raw accelerometer data is accurate in static conditions but highly sensitive to vibration and dynamic acceleration. A complementary filter addresses both limitations by fusing the two sources.

## 11.2 Algorithm

Orientation is estimated using the following fusion equation:

orientation = alpha \* gyroscope_integration + (1 - alpha) \* accelerometer_angle

With alpha = 0.98, the gyroscope contributes 98% (smooth, low-latency response to motion) and the accelerometer contributes 2% (long-term drift correction). Roll and pitch are computed independently. Yaw estimation requires a magnetometer and is excluded.

Roll from accelerometer:

roll = atan2(ay, az) \* 180 / pi

Pitch from accelerometer:

pitch = atan2(-ax, sqrt(ay^2 + az^2)) \* 180 / pi

Gyroscope integration:

gyro_roll = prev_roll + gx \* dt

gyro_pitch = prev_pitch + gy \* dt

## 11.3 Implementation

| **File**         | **Role**                                                        |
|------------------|-----------------------------------------------------------------|
| include/filter.h | Orientation struct, filter_init() and filter_update() interface |
| src/filter.cpp   | Complementary filter implementation                             |

dt is computed from millis() at each loop iteration for accurate time integration.

## 11.4 Verified Output (stationary)

| **Parameter** | **Value**  |
|---------------|------------|
| Roll at rest  | ~0.00 deg  |
| Pitch at rest | ~0.00 deg  |
| Noise range   | +-0.35 deg |

Orientation responds correctly to physical rotation of the sensor. No observable drift during short-duration tests.

# **13. Phase 4 — Dataset Collector Firmware**

## 13.1 Motivation

Before training data can be assembled, the firmware must emit windowed, feature-extracted samples in the exact numerical format the model will later consume, rather than raw per-sample streams. Performing feature extraction on-device validates that the same extraction routine used for training is reusable at inference time, eliminating train/inference skew.

An initial design considered a physical push-button to mark individual gesture events. This was rejected: button-triggered capture is noisy and impractical for repeated single-hand data collection sessions. A session-based serial command protocol was adopted instead — one command starts a labeled recording session that persists across many consecutive gesture repetitions.

## 13.2 Architecture

| **File**                              | **Role**                                                     |
|---------------------------------------|--------------------------------------------------------------|
| include/collector.h                   | Window size / sample rate constants, public interface        |
| src/gesture-recognition/collector.cpp | Session state machine, feature extraction, CSV serialization |

main.cpp was extended to call collector_init() once at startup and collector_check_command() / collector_add_sample() each loop iteration, after the IMU read and filter update. The complementary filter's orientation output (roll/pitch) is computed but intentionally not passed to the collector — consistent with the locked design constraint that gesture classification must be orientation-invariant.

## 13.3 Session-Based Recording Protocol

| **Command** | **Effect**                                        |
|-------------|---------------------------------------------------|
| s           | Start/continue a SHAKE-labeled session (label 0)  |
| r           | Start/continue a ROTATE-labeled session (label 1) |
| i           | Start/continue an IDLE-labeled session (label 2)  |
| x           | Stop the current session                          |
| h           | Reprint the CSV header                            |

A session remains active, silently emitting one CSV row per completed window, until x or a new label command is received.

## 13.4 Windowing and Feature Extraction

| **Parameter**       | **Value**                                 |
|---------------------|-------------------------------------------|
| Sample rate         | 50 Hz (20 ms loop delay)                  |
| Window size         | 50 samples = 1 s                          |
| Features per window | 12 (mean + RMS of ax, ay, az, gx, gy, gz) |

Feature extraction runs entirely on-device per completed window, using the same calibrated accelerometer/gyroscope values produced by the Phase 2 pipeline. No absolute roll/pitch is included in the feature set.

## 13.5 Output Format

CSV emitted over serial, one row per completed window:

gesture,ax,ay,az,gx,gy,gz,ax_rms,ay_rms,az_rms,gx_rms,gy_rms,gz_rms

gesture is the numeric label captured at the start of the row's window (0 = shake, 1 = rotate, 2 = idle). Rows are assembled offline into per-class CSV files for the training pipeline.

## 13.6 Issue Identified and Corrected Prior to Commit

Code review prior to staging identified that \_sampleCount was not reset on a label transition (s/r/i) or on x. In practice this allows a partially filled window from one session to carry over into the next, so a window can be assembled from samples belonging to two different gestures while being emitted under a single label — a silent mislabeling defect that would have degraded dataset quality from the first recording session onward. Fixed by resetting \_sampleCount = 0 on every label transition and on stop, discarding any partial window at session boundaries.

A related build-configuration issue was corrected in platformio.ini: the i2c-scan and ssd1306-test tool environments declared their src_dir override in bare sections rather than inside their corresponding \[env:...\] blocks, where PlatformIO requires it. This was later superseded entirely by the Section 14 restructuring.

## 13.7 Current Status

Collector firmware compiles and runs correctly against the fixed session-boundary logic described above. No training data has been recorded yet — the next session begins the actual capture (≥200 windows per class for shake, rotate, idle).

# **14. Build System Restructuring — Multi-Environment Source Isolation**

## 14.1 Motivation

As the project grew to include standalone diagnostic firmware (i2c_scan) alongside the main gesture-recognition application, and with OLED bring-up testing (ssd1306_test) planned as a distinct firmware, a mechanism was needed to build multiple independent setup()/loop() programs from a single repository without cross-contamination between builds.

## 14.2 Root Cause of the Original Approach's Failure

The initial approach attempted to override src_dir on a per-environment basis inside \[env:NAME\] blocks in platformio.ini. This is not supported by the PlatformIO Core version used by this project: src_dir is not a recognized per-environment option. Confirmed directly via build output:

Warning! Ignore unknown configuration option \`src_dir\` in section \[env:i2c-scan\]

With this misconfiguration, environments intended to build diagnostic tools were silently compiling the main firmware's src_dir instead — a defect that could go unnoticed, since the build itself did not fail, it simply compiled the wrong program.

## 14.3 Adopted Solution: build_src_filter

build_src_filter is supported per environment and allows include/exclude glob patterns within a single shared src_dir. The repository was restructured so that each independent firmware lives in its own subdirectory of src/, and each environment's build_src_filter includes only its own subdirectory while explicitly excluding the others:

| **Directory**            | **Firmware**                                                           | **Environment**               |
|--------------------------|------------------------------------------------------------------------|-------------------------------|
| src/gesture-recognition/ | Main application — IMU driver, complementary filter, dataset collector | gesture-recognition (default) |
| src/i2c_scan/            | Standalone I2C bus diagnostic tool                                     | i2c-scan                      |
| src/ssd1306_test/        | OLED bring-up test (hardware currently defective, deferred)            | ssd1306-test                  |

build_src_filter = +\<gesture-recognition/\> -\<i2c_scan/\> -\<ssd1306_test/\>

default_envs = gesture-recognition in \[platformio\] ensures an unqualified pio run builds only the primary firmware. The previous tools/ directory, which held diagnostic tool source outside of src_dir and therefore could not be reached by build_src_filter, was removed; its contents were relocated into src/.

## 14.4 OLED Retest — Deferred, Environment Ready

The ssd1306-test environment and its Adafruit SSD1306/GFX library dependencies are now correctly isolated and ready to build in advance of the actual hardware retest. The underlying hardware issue documented in Section 6 remains unresolved and is not being re-investigated at this time — this restructuring only prepares the build environment so the retest can proceed later without further tooling work.

## 14.5 Verification

Each environment was confirmed to compile only its intended source file(s) via verbose build output (pio run -e \<env\> -v), checking the Compiling entries against the expected file set.

# **16. Phase 5 — TinyML Model Training and On-Device Inference**

## 16.1 Dataset Capture Summary

Labeled data was captured using the session-based collector protocol described in Section 13, across 5 distinct arm orientations per class (up, forward, down, diagonal-up, diagonal-down), 5 sessions of 10 seconds each. The first and last window of every session are discarded at capture time to remove the transition into and out of the gesture, per the protocol already documented.

| **Class** | **Label** | **Windows captured** |
|-----------|-----------|----------------------|
| shake     | 0         | 120                  |
| rotate    | 1         | 125                  |
| idle      | 2         | 120                  |
| Total     |           | 365                  |

Class balance is effectively even (within 5 windows across all three classes), so no resampling or class-weighting was required before training.

## 16.2 Exploratory Data Analysis

Per-class boxplots of all 12 features and a 2D scatter of the two most visually separating features (ax_rms vs gx_rms) were generated to verify separability before committing to a training run. The three classes form visually disjoint clusters with no observable overlap in the scatter projection. gy_rms is the single most discriminative feature (idle mean approx. 1.7, rotate approx. 168, shake approx. 61), consistent with rotate being a sustained rotation captured strongly on the gyroscope Y axis.

## 16.3 Feature Normalization

Features mix physical units (m/s2 for accelerometer, deg/s for gyroscope) with very different numeric ranges (e.g. gy_rms spans approximately 0.23 to 195, while ax spans approximately -3.9 to 2.7). StandardScaler (zero mean, unit variance per feature) was adopted to prevent gyroscope-derived features from dominating the training gradient purely due to magnitude. The scaler is fit only on the training split to avoid validation leakage, and its per-feature mean/standard deviation are exported for use on-device, since the same normalization must be applied to raw features before inference.

## 16.4 Model Architecture and Training

| **Layer**       | **Output shape** | **Parameters** |
|-----------------|------------------|----------------|
| Dense (ReLU)    | 64               | 832            |
| Dense (ReLU)    | 32               | 2,080          |
| Dense (softmax) | 3                | 99             |
| Total           |                  | 3,011          |

Training configuration: 80/20 stratified train/validation split, Adam optimizer, sparse categorical cross-entropy loss, 50 epochs, batch size 16.

| **Class** | **Precision** | **Recall** | **F1-score** |
|-----------|---------------|------------|--------------|
| shake     | 1.00          | 1.00       | 1.00         |
| rotate    | 1.00          | 1.00       | 1.00         |
| idle      | 1.00          | 1.00       | 1.00         |

Validation accuracy: 100% (73/73), with a fully diagonal confusion matrix (24 shake, 25 rotate, 24 idle, zero cross-class errors).

Methodological note (known limitation): the train/validation split was performed at the window level, not the session level. Because windows from the same 10-second session are highly autocorrelated, it is likely that windows from a given session appear in both the training and validation sets, which inflates the reported accuracy relative to a true out-of-session generalization measurement. Given the clean cluster separation already observed in the EDA scatter, true generalization performance is plausibly still high, but the exact 100% figure should not be read as an unbiased estimate. A session-level split is listed as a correction for a future iteration (Section 17).

## 16.5 Quantization and On-Device Deployment

The trained model was quantized post-training to full int8 (both input and output tensors) using the TFLite Converter, with a representative dataset built from the first 100 normalized training samples. Exported artifacts: gesture_model.tflite (8,200 bytes), model_data.h (C byte array for firmware inclusion), and scaler_params.h (per-feature mean and standard deviation for on-device normalization).

The initial choice of TFLite Micro runtime, espressif/esp-tflite-micro, failed to build under PlatformIO: its git distribution does not vendor its third-party dependencies (flatbuffers, gemmlowp/fixedpoint), which are normally resolved automatically by the ESP-IDF component manager but are invisible to PlatformIO's dependency resolution. This is a known limitation of consuming that repository outside of ESP-IDF. It was replaced with johnosbb/MicroTFLite, an Arduino/PlatformIO packaged distribution of the same runtime with all dependencies vendored, exposing a simplified API (ModelInit / ModelSetInput / ModelRunInference / ModelGetOutput) that also performs int8 quantization and dequantization internally.

Tensor arena: 8,192 bytes, a conservative starting allocation for a model of this size (3,011 parameters). A new firmware module, inference.h / inference.cpp, mirrors the window accumulation and mean/RMS feature extraction already implemented in collector.cpp, but runs continuously whenever collector_is_recording() is false — ensuring live inference and labeled dataset capture never operate on the same sample stream simultaneously.

## 16.6 Physical Feedback — LED Mapping

| **GPIO** | **Class**                                     | **Behavior**               |

| 4        | shake                                         | 300 ms pulse, non-blocking |
| 23       | rotate                                        | 300 ms pulse, non-blocking |

The main loop's 20 ms delay is load-bearing for the IMU sample rate; a blocking delay on LED output would perturb the sampling window and was avoided for that reason.

## 16.7 Current Status and Known Issues

- Live inference and dataset capture coexist correctly in the same firmware build, gated by collector_is_recording().

- Under normal, non-gesture arm movement, the classifier occasionally reports shake instead of idle. Root cause: the idle class was captured only as static, stationary poses across 5 orientations, and was never shown ambient low-level motion during training — a category gap in the dataset, not a firmware defect.

- Physical LED output is confirmed working. Root cause of the initial failure: the ground connection was taken from the breadboard rail shared with the IMU (the partially failed rails already documented in Section 3.2), not a GPIO or firmware issue. Resolved with a direct jumper to the ESP32's own GND pin. LEDs were relocated to GPIO4 (shake) and GPIO23 (rotate) during debugging; GPIO25/GPIO26 remain electrically valid and were not the cause of the failure.
